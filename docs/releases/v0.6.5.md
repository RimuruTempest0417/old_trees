# v0.6.5 — 23514 再修：改成「seed 自己修」，並附一支可單獨執行、會印診斷的修復檔

## 一、為什麼 v0.6.4 還是失敗

v0.6.4 的修復是放在 `init.sql` **最前面**的升級段落（先刪舊 CHECK、再建新的）。
若那段沒有被執行，後面的 seed 就會照樣撞 23514。最常見的原因是
**Supabase SQL Editor 只會執行「選取範圍」**：只要編輯器裡有任何選取（例如您上次貼上後
殘留的選取、或只反白了中間一段），按 Run 就只跑那一段，前面的升級段落不會生效。

（也就是說：檔案本身沒問題，而是執行的範圍不完整。這種「依賴前面章節」的設計本身也太脆弱。）

## 二、這一版的改法：不依賴前面章節

**在 `seed.sql` 的 `truncate` 之後、所有 `insert` 之前，加入一段「限制條件自我修復」**：

```sql
do $$ ... loop
  -- 移除任何涉及 sites.geo_precision / trees.grade / trees.health 的 CHECK（依實際名稱，不論叫什麼）
  execute format('alter table %s drop constraint %I', r.tbl, r.conname);
end $$;
alter table public.sites drop constraint if exists sites_geo_precision_check;
alter table public.sites add constraint sites_geo_precision_check
  check (geo_precision in ('official','exact','approx','parish'));
-- trees.grade、trees.health 同樣處理
```

為什麼放在這裡最安全：此時資料表**剛被 truncate、沒有任何資料**，重建限制條件不會有
「舊資料違反新條件」的問題，也不需要任何正規化。**即使您只貼 seed 這一段並執行，也能自己修好。**

`schema.sql` 檔頭原本的升級段落仍然保留（雙重保險）。

## 三、新增 `supabase/fix_23514.sql`（可單獨執行）

一支約 80 行的小檔，只做限制條件，不會碰任何資料，而且**會印出診斷結果**：

1. 印出版本字串（`v0.6.5-fix23514`）與時間——若顯示的不是這個版本，代表貼到了舊檔案。
2. 印出目前 `sites`／`trees` 上所有 CHECK 限制條件與定義。
3. 移除任何涉及 `geo_precision`／`grade`／`health` 的 CHECK（依目錄中的實際名稱，不管叫什麼）。
4. 重建為新版定義。
5. 再印一次結果（`sites` 那條應包含 `official`）。

## 四、驗證（PGlite 實跑 PostgreSQL 16）

- 情境：把 `sites_geo_precision_check` 換成舊版（只允許 `exact/approx/parish`）。

  `CHECK (geo_precision = ANY (ARRAY['official','exact','approx','parish']))`，
  接著執行 `seed.sql` 成功，`geo_precision='official'` 的地點共 **127** 筆。
- 只跑 `seed.sql`（完全不執行 schema 升級段）：也能自我修復並成功寫入。
- `npm run check`：44 個檔案語法全過；`npm test`：**10 組、131 項全過**（新增兩項回歸測試）。

## 五、您要做的（建議順序）

1. 先跑 `supabase/fix_23514.sql`（**整份貼上 → Cmd/Ctrl + A 全選 → Run**），確認第 1 步印出的版本是
   `v0.6.5-fix23514`、第 5 步的 `sites` 定義裡有 `official`。
2. 再跑最新的 `supabase/init.sql`（同樣先全選再 Run）。

> **重要習慣**：在 Supabase SQL Editor 按 Run 之前，先按 `Cmd/Ctrl + A` 全選，
> 確保執行的是整份內容，而不是殘留的選取範圍。
