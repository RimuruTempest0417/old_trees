# v0.11.0 — 官方值優先（#1132 查核）＋ 監測時間序列（E）

這一版有兩件事：先把第 1132 號樹查清楚並修正分級來源的問題，然後做完 **E：監測時間序列**。

## 一、第 1132 號樹查核結果：官方兩個來源不一致，改用自然網現行值

**查核方式**：抓市政署自然網原始紀錄（`oldtrees_c.json`）逐欄比對本機三份資料（`data/iam_trees.json`、`data/snapshot.json`、畫面顯示值）。

| 欄位 | 《古樹名錄》CSV | 市政署自然網現行值 | 判定 |
| --- | --- | --- | --- |
| 分級 | 三級 | **不分級** | **採自然網值**（見下） |
| 健康狀況 | 一般 | 一般 | 一致 |
| 樹齡 | 14 年 | 14 年 | 一致 |
| 胸徑 | — | `treeDiameter = 12.00,14.00`（2 支主幹） | 取最大 14.00 公分 |
| 胸圍 | — | `treeSurround = 37.7,44.0` | 取同一支 44.0 公分 |

**為什麼判定自然網值才對**：14 年的樹不可能是「三級」（該級距為 100–299 年）；
官方 5 株「不分級」的樹齡都在 6–35 年（#66、#67、#1131、#1135、#1132），型態一致。
另外 `37.7 = π × 12.00`、`44.0 = π × 14.00` 完全吻合，證明官方兩個欄位逐支對應、
我們「取最大胸徑那支」（14.00 / 44.0）的顯示無誤 —— 這一株**只有分級用錯了來源**。

**修法：官方值優先（`officialFirst()`）**

- 新增 `lib/repo.js` 的 `officialFirst(row)`：分級與健康狀況一律採 `official_grade`／`official_health`（自然網現行值），
  《名錄》值保留在 `listing_grade`／`listing_health`，原始資料檔一字未改。
- 套用到所有顯示路徑：`allTrees()`（快照與 Supabase 兩種模式）、單株詳情、地圖彈窗、優先保育名單、列印卡片。
- **統計與篩選同源**：`overview()` 與 `parishStats()` 不再走 `rpc_overview`／`v_parish_stats` 的 SQL 統計
  （那是資料庫的《名錄》欄位），改為兩種模式都由 `allTrees()` 計算；Supabase 模式下若用官方分級／健康狀況篩選，
  改為取回後在 JS 內以顯示值篩選，避免「畫面上看不到卻篩得出來」。
- 單株詳情「資料核對」文案改為：《古樹名錄》原列「三級」，市政署自然網現行為「不分級」— 本頁以官方現行值為準。

**影響範圍（全部核對過）**：658 株中僅 **5 株**有此差異 —— 分級 1 株（#1132）、健康狀況 4 株
（#548、#627、#638、#641：名錄「一般」→ 自然網「健康」）。修正後畫面上的官方分佈為
一級 1、二級 6、三級 646、不分級 5；健康 215、一般 422、瀕危 21，與官方來源檔逐筆一致。

**未改動的一項**：樹齡仍呈現《名錄》值（#619 名錄 155 年／市政署 115 年），差異在「資料核對」中標明。
要不要比照改以自然網值為準（會影響優先保育評分與分析結果）屬另一個決定，這一版不動。

**新增測試** `tests/official-values.test.js`（7 項）：`officialFirst()` 的行為與缺值回退、
#1132 的逐欄驗證（含胸圍與官方胸徑自洽）、658 株顯示值必須等於官方值、
**官方與名錄的差異必須剛好是這 5 株**（資料一更新就提醒重新核對）、統計與篩選同源、堂區統計總和等於總覽。

## 二、監測時間序列（E）

一株古樹的變化，只有「同一株、不同時間的兩次觀測」才說得出來。這一版把三個有出處的來源接成一條序列：

| 來源 | 內容 | 時間點 |
| --- | --- | --- |
| `listing` | 《古樹名錄》官方值 | 較早的官方版本（未載日期，視為最早） |
| `official` | 市政署自然網現行值的**逐次快照** | 每次官方內容變更存一份帶日期的快照 |
| `field` | 師生實地考察紀錄（`field_records`） | 觀察日期、觀察者、健康狀況、樹高／胸徑／冠幅… |

- **官方只公布現行值、沒有歷史值**，所以我們自己存：新增 `scripts/snapshot-observations.mjs`，
  官方名錄內容有變更時存一份 `data/observations/<日期>.json`（只存監測欄位：健康狀況、分級、樹齡、樹高、胸徑、胸圍、冠幅），
  並重建 `lib/official-history.js` 供 API 與前端使用；**內容沒變不重複存檔**（以內容雜湊判斷，避免一年 365 份一樣的快照）。
  已納入每日擷取 workflow，`npm run build:observations` 也可手動執行，`--check` 供測試驗證是否同步。
- **新 API** `GET /api/monitoring`：`?tree=<編號>` 回單株完整序列（觀測點、逐次差異、趨勢、異常、快照清單），
  `only=changed｜attention｜field` 篩選，`rows=1` 附每株變動摘要；回傳 `summary`、`method`（三個來源與規則）、官方資料履歷。
- **新分頁「監測」**（第十個分頁）：五張概況卡（監測株數、官方快照數與起日、官方資料變動株數、已有考察紀錄株數、需人工確認株數）、
  「怎麼看這一頁」說明、單株查詢（`#/monitoring?tree=1132`）、變動／需確認／有紀錄的切換清單、單株的觀測點表、
  逐次差異、趨勢圖（Chart.js）、異常清單，並可複製摘要與匯出 CSV。
- **判斷規則全部可解釋**：胸徑減少 ≥ 0.5 公分、樹高減少 ≥ 0.2 公尺、實地看到的健康惡化 → 需確認（warn）；
  官方分級／健康狀況變動 → 資訊（info，官方資料更新，不是我們判定的異常）；距上次觀測 > 730 天 → 提醒複查。
- **不硬湊**：缺值不內插、不用平均值填補，只比較兩邊都有值的欄位；可量測時間點不足兩個或跨距 < 30 天，
  就只顯示「無法擬合」並寫出原因。
- 目前 658 株中已有 5 株看得到真實的官方變動（#1132 分級三級→不分級；#548／#627／#638／#641 健康一般→健康），
  其餘株的序列會隨每日擷取與實地考察累積 —— 這是設計上的必然，頁面上明說，不假裝有資料。

**新增測試** `tests/monitoring.test.js`（17 項）：純函式（序列組成與排序、缺值不補、趨勢邊界、異常規則、複查提醒、概況統計）、
真實資料（#1132 的分級更新、全站變動株數必須等於名錄與官方現行值的差異株）、官方快照產生器 `--check`、
`/api/monitoring` 端到端（含 404 與**回應契約**）。

**過程中抓到的兩個自己的 bug**：

1. `/api/monitoring` 精簡模式把 `items[].changes` 換成筆數（數字），前端 `r.changes.map(...)` 直接
   `TypeError` → 整個監測分頁顯示「載入時發生錯誤」。已改為 `changes` 一律是陣列（精簡模式只省略 `points`／`steps`），
   測試加上契約斷言，前端也加了 `arr()` 防禦。
2. 監測清單預設沒有帶 `only=changed`，標題寫「官方資料有變動的株」卻把 658 株全列出來。已改為預設只列有變動的株，
   並提供「有變動／需確認／有考察紀錄／全部」切換。
