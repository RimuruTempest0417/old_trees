# v0.11.1 — 修好線上單株詳情仍顯示《名錄》舊分級（Supabase 模式）

v0.11.0 上線後在**線上**發現一個只在 Supabase 模式才會出現的問題：同一株樹在兩個頁面不一致。

## 症狀

- `/api/trees`（地圖清單）、優先保育名單、列印：**#1132 分級＝不分級**（正確，官方現行值）
- `/api/tree/1132`（單株詳情）：**分級＝三級**（《名錄》舊值）、且沒有 `listing_grade`／`listing_health`
- 因此線上點開 #1132 的詳情，看到的仍是「三級」，與列表不一致

## 根因

`lib/repo.js` 的 `getTree()` 有兩條分支：

```js
if (DATA_SOURCE === 'supabase') {
  ...
  return { ...r, age_years: num(...), height_m: num(...), ... };   // ← 直接回 v_trees 原始列
}
const t = snapshot.trees.find(...);
return t ? normalizeTreeRow(enrich(t)) : null;                     // ← 走正常化，含 officialFirst
```

v0.11.0 把「官方值優先」實作在 `normalizeTreeRow()`／`allTrees()`／`findTrees()` 裡，
但 **Supabase 分支的 `getTree()` 繞過 `normalizeTreeRow()`**，所以那條路徑完全沒套用到。
本機示範（snapshot）模式走的是另一條分支，因此本機測試全過、只有線上出錯
——與 v0.7.1（Supabase 查詢形狀）、v0.9.1（路由載入器）同一類「本機測不到的模式差異」。

## 修法

`getTree()` 的 Supabase 分支改為 `return normalizeTreeRow(rows[0])`，兩條分支回傳同一組欄位
（含 `listing_grade`／`listing_health` 與官方胸徑／胸圍），分級、健康狀況、多主幹量測在兩種模式一致。

## 測試守門

`tests/supabase-path.test.js` 追加第 5 項：以假的 `fetch` 攔截 `v_trees`，回傳
「資料庫分級三級、官方分級不分級」的列，然後斷言：

- `getTree('1132').grade === '不分級'`（顯示值必須是官方現行值）
- `listing_grade === '三級'`（《名錄》值仍保留給「資料核對」）
- `girth_cm === 44`、`stem_measures` 含逐支量測

**守門有效性已實測**：把修正暫時還原 → 該測試紅燈（`單株詳情的分級必須是官方現行值`）→ 還原修正 → 全綠。

## 驗證

- `npm run check`：67 個檔案語法通過
- `npm test`：**17 組 256 項全過**
- 線上部署後以 `/api/tree/1132` 與 `/api/monitoring?tree=1132` 讀回確認：

```json
{ "grade": "不分級", "official_grade": "不分級", "listing_grade": "三級", "health": "一般" }
```

## 教訓（已寫進 skill）

新增或修改「顯示值的來源」時，**要逐一檢查每一條依模式分岔的取徑**（`getTree`／`allTrees`／`findTrees`／
`rpc_*`），並對 Supabase 模式寫一條迴歸測試 —— 本機示範模式只走其中一條，測不到另一條。
