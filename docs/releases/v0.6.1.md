# v0.6.1 — 部署阻礙排除：單一 Serverless Function ＋ 資料庫就地升級

本次修正您在 Vercel 與 Supabase 遇到的兩個阻礙。兩者都不是功能錯誤，而是**結構與版本升級**的問題。

## 一、Vercel：`No more than 12 Serverless Functions can be added to a Deployment (Hobby plan)`

**原因**：Vercel Hobby 方案限制每個 Deployment 最多 12 個 Serverless Function，而 `api/` 底下
**每一個 `.js` 檔都算一個**。本專案原本有 12 個端點檔 ＋ 1 個動態路由（`api/tree/[tree_no].js`）
＝ **13 個**，因此建置直接失敗。

**替代方案（採用）**：把所有 handler 搬到 `lib/routes/`（`lib/` 不算 Serverless Function），
`api/` 只留**一個**萬用入口 `api/[[...route]].js`，由 `lib/router.js` 依路徑分派。

- 端點網址完全不變：`/api/health`、`/api/trees`、`/api/tree/66`、`/api/field-records` … 照舊。
- **不論以後新增多少端點，都只佔 1 個 Function**，不會再撞上限。
- 不需要升級 Vercel Pro（每月 20 美元）。
- 本機 `dev-server` 也改用同一套 `lib/router.js`，因此**本機與線上的路由行為一致**（以前是兩套實作）。
- 新增測試守住結構：`api/` 只要超過 1 個 `.js` 就會紅燈。

其他方案（未採用）與原因：升級 Pro（要花錢）；把 13 個檔合併成 12 個（下次加端點又會爆）；
改用 Netlify／Cloudflare（要重寫部署設定，效益不明顯）。

## 二、Supabase：`column "geo_precision" of relation "public.trees" does not exist`

**原因**：`create table if not exists` 對**已存在**的舊表**不會**補欄位。您的資料庫裡是舊版
`init.sql` 建立的 `trees` 表（沒有 `geo_precision`、`official_*` 等後來新增的欄位），
因此貼上新版 `init.sql` 時，前面建立表的語句被跳過，後面的 seed 一 insert 就失敗，
整段交易（`begin … commit`）回滾——資料沒有壞，只是沒有更新。

**替代方案（採用）**：在 `schema.sql`／`init.sql` **開頭**加入一段可重複執行的「版本升級」：

```sql
alter table if exists public.trees add column if not exists geo_precision text;
-- …共 8 張表、89 個欄位，並補上必要的 CHECK 條件
```

- 放在檔首並用 `alter table if exists`，因此與 `create table` 的先後順序無關：
  全新資料庫執行時表還不存在，全部跳過；舊資料庫則**就地補齊**缺少的欄位。
- 連 `default` 一起補（例如 `in_namelist default true`），避免升級後出現 NULL。
- **不需要**刪表重建，實地考察紀錄不會遺失。
- 新增回歸測試：模擬「缺欄位的舊資料庫」→ 執行 `schema.sql` ＋ `seed.sql` → 必須成功寫入 658 筆。

其他方案（未採用）與原因：請您 `drop table` 重建（會清掉資料，且要手動重來）；
只給您一段臨時修補 SQL（下次改版又會遇到同樣問題，治標不治本）。

## 三、您的操作步驟

1. **Supabase**：SQL Editor → 貼上最新的 `supabase/init.sql`（現在約 1784 行）→ Run。
   這次會先補齊缺少的欄位，再寫入 658 筆官方資料；`trees`、`sites` 等名錄資料會被重新整理，
   但**實地考察紀錄（`field_records`）不會被清掉**（見第四節的實測與修正）。
2. **Vercel**：把最新 `main` 重新部署（Deployments → 最新一次 → Redeploy，或直接 push 觸發）。
   這次只會有 1 個 Serverless Function，建置應該通過。
3. 部署完成後開 `https://<您的網址>/api/health`，`data_source` 應顯示 `supabase`，網站上的「示範模式」提示會消失。

## 四、順手抓到的一個會弄丟資料的問題（已修正）

準備升級腳本時實測發現：`seed.sql` 重新初始化時會執行
`truncate table public.trees, public.sites, … restart identity cascade`；
由於 `field_records.tree_no` 原本對 `trees` 設了外鍵，PostgreSQL 的
`TRUNCATE … CASCADE` **會連帶把實地考察紀錄一起清空**（PGlite 實測：有外鍵 → 剩 0 筆；
無外鍵 → 保留）。也就是說，您只要重跑一次 init.sql，學生辛苦記錄的考察就會消失。

已修正：`field_records.tree_no` 改為**軟性參照**（純文字比對，不設外鍵），並在升級段落中加入
`alter table if exists public.field_records drop constraint if exists field_records_tree_no_fkey;`
移除舊資料庫上已存在的外鍵。同時新增回歸測試：先寫入一筆考察紀錄 → 重新 seed → 必須仍存在。
